# S88 driver notes

Implementation: [`python/pitraincontroller/s88/driver.py`](../python/pitraincontroller/s88/driver.py),
service entrypoint [`python/pitraincontroller/s88/service.py`](../python/pitraincontroller/s88/service.py).

## Status: implemented, **not yet verified against real hardware**

The S88 daughterboard (`docs/reference/hardware-manual-v4.md` calls out
J8/RJ1/RJ2 explicitly as "being revised separately") isn't finalized or
built yet. Everything below is the best-grounded design given what's
confirmed so far — treat the polarity assumptions as the first thing to
check once real boards exist.

## What's confirmed

- **Pin map**: GPIO22 CLOCK, GPIO23 LOAD, GPIO24 RESET (all outputs from
  the Pi), GPIO17 DATA (input, level-shifted 5V→~3V by an on-board
  resistor divider). Confirmed identical in both the original brief and
  the PCB Design v4.0 manual.
- **Module chip**: the S88N module schematic uses **74HC165** parallel-
  load shift registers (confirmed by inspecting the schematic directly).
  This is the classic S88 shift-register model, not a differential
  RS485-style "true S88-N" redesign — the RJ45/CAT5 connectors
  (`RJE561881410`) appear to be for cabling convenience, carrying the
  same CLOCK/LOAD/RESET/DATA signals rather than a different electrical
  protocol.
- **Timing minimums**: per the widely-cited opendcc.de S88 timing page,
  clock cycle ≥ ~30µs (≥15µs high/low each) — a *minimum*, not a
  maximum. The driver defaults to a 150µs half-period (300µs/cycle,
  ~10x margin) specifically so ordinary Python/OS scheduling jitter
  can't violate the spec; this is a deliberate safety margin, not a
  measured requirement, and can be tightened once real hardware is
  available and scan-rate matters more than headroom.
- **Bus speed vs. "occupied" semantics**: the official Marklin CAN
  protocol spec (section on S88 Polling compatibility mode) describes
  classic S88 as *register-based, cleared by reading* — a momentary
  sensor trigger latches "on" until explicitly read/reset. This is why
  RESET exists as a real signal even on boards built from plain shift
  registers with no dedicated reset pin of their own (the daughterboard
  schematic includes CD4044 R-S latch ICs alongside the 74HC165s, which
  is consistent with this: the latches hold "seen since last reset",
  and the 165s are just the shift-out mechanism read on each poll).

## What's assumed, pending hardware confirmation

Signal polarity isn't specified anywhere in the brief or the manual —
both just label the pins by function ("S88 LOAD (out)"), not electrical
level. Current defaults, both flippable with a one-line config change
(`S88Config.load_active_high` / `.reset_active_high` in
`common/config.py`, or the `PITC_S88_LOAD_ACTIVE_HIGH` /
`PITC_S88_RESET_ACTIVE_HIGH` env vars):

| Signal | Default polarity | Rationale |
|---|---|---|
| LOAD | active-**LOW** | Matches the 74HC165's SH/LD# pin directly: LOW = parallel-load, HIGH = shift mode. Confirmed chip, so this is the higher-confidence default. |
| CLOCK | active-**HIGH** pulse | 74HC165 shifts on the rising edge; driver reads DATA *before* each clock pulse (bit 0 is valid immediately after LOAD releases, no clock needed yet). |
| RESET | active-**HIGH** pulse, once per scan, before LOAD | Matches the brief's literal 3-step description ("Pulse RESET... Pulse LOAD... Pulse CLOCK..."); exact polarity unconfirmed since 74HC165 has no reset pin of its own — whatever RESET actually drives on the daughterboard (likely the CD4044 latches) determines the real answer. |

## Also not yet wired up

- **Module/bit count**: defaults to 5 modules × 16 bits = 80 contacts
  (`PITC_S88_MODULE_COUNT` / `PITC_S88_BITS_PER_MODULE`), matching the
  brief's stated maximum. Confirm against whatever module count is
  actually populated once boards exist.
- **CAN device UID / hash**: S88 change events are published onto `can0`
  as proper Marklin CAN "S88 Event" frames (command `0x11`), but the
  `device_uid` is a static placeholder and the CAN-ID `hash` field is
  *not* the real Marklin hash-collision-avoidance algorithm — just the
  device UID reused as a stand-in. Fine for bench testing against a
  single fixed listener (Rocrail, `candump`); not spec-correct for
  sharing a live bus with other real CS2/CS3 devices until M4 (the
  gateway) implements the real device-UID assignment handshake and hash
  algorithm, both of which are protocol-level concerns that belong there
  rather than duplicated in the S88 service.
