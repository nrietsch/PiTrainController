# S88 driver notes

Implementation: [`python/pitraincontroller/s88/driver.py`](../python/pitraincontroller/s88/driver.py),
service entrypoint [`python/pitraincontroller/s88/service.py`](../python/pitraincontroller/s88/service.py),
bring-up tool [`python/pitraincontroller/s88/dump.py`](../python/pitraincontroller/s88/dump.py).

## Status: being brought up on real hardware

The home-built S88 daughterboard (see `docs/reference/hardware-manual-v4.md`,
J8/RJ1/RJ2) doesn't exist yet. First real test is with a Viessmann 5217
module on J5/J4.

The original driver used a LOAD-active-**low** sequence with no clock
pulse during LOAD, guessed from the 74HC165 chips on the planned
daughterboard. That was wrong for the S88 *bus*, and a standard module
read all 1s no matter what: the 5217 uses CD4014 shift registers, which
**load on a clock edge while LOAD is high**; with LOAD idling high it
sat permanently in load mode, so every bit read was the same input.

The driver now follows the sequence the 2016 PiCanS88 ran on real
modules (`docs/reference/legacy-picans88-2016/PiCanS88/S88UDP.cpp`,
`HandleS88Events`), which also matches the OpenDCC S88 description
("LOAD goes to 1, then a shift clock is applied ... the next step is a
RESET pulse (also active high) ... now the shift occurs with LOAD = 0"):

1. LOAD high
2. one CLOCK pulse while LOAD is high (the load edge for 4014-style modules)
3. RESET pulse (high)
4. LOAD low
5. for each bit: read DATA, then pulse CLOCK

LOAD, RESET and CLOCK all idle **low**. Whether this works against the
5217 is still to be confirmed on the bench. Not yet verified: the
5217 itself may be faulty; use `python3 -m pitraincontroller.s88.dump`
(stop `pitraincontroller-s88` first) to see the raw bits.

## What's confirmed

- **Pin map**: GPIO22 CLOCK, GPIO23 LOAD, GPIO24 RESET (outputs from the
  Pi), GPIO17 DATA (input). Same pins the 2016 PiCanS88 used, and
  identical in both the brief and the PCB Design v4.0 manual.
- **DATA input circuit (from the PCB netlist and measured on a real
  board)**: J5 DATA goes through R10 (10k) to GPIO17, which has R11
  (15k) to ground, and R4 (1.8k) pulls the DATA line up to 5V. With
  nothing connected, GPIO17 therefore reads **high** (about 2.3V
  measured at the pin). A dumped bit vector of all 1s with nothing
  plugged in is normal, not a fault.
- **J5/J4 physical order**, with RJ1 in the bottom-left corner,
  reading left to right on J5: Data, GND, Clock, Load, Reset, VS88
  (the classic S88 order). The schematic numbers these pins from the
  other end (pin 1 = VS88, pin 5 = GND, pin 6 = Data), while the
  hardware manual's table numbers them left to right. Go by physical
  position, not pin number.
- **Timing minimums**: per the widely-cited opendcc.de S88 timing page,
  clock cycle >= ~30us (>= 15us high/low each) — a *minimum*. The
  driver defaults to a 150us half-period for margin against Python/OS
  jitter. HEF4014 setup/hold at 5V are tens of ns.
- **Latch behaviour**: classic S88 modules store momentary contacts in
  4044 RS latches that RESET clears, so a contact shorter than the scan
  interval is still seen on the next scan (the 5217 schematic shows
  4044s feeding two 4014s).

## Polarity and the planned daughterboard

The Pi drives the bus lines directly. LOAD is an active-HIGH pulse, as
standard S88 modules expect. A daughterboard built from 74HC165s has an
active-LOW, asynchronous SH/LD# pin, so it must invert LOAD on the board
(the extra clock pulse during LOAD is harmless to those chips), or the
host can be switched with `PITC_S88_LOAD_ACTIVE_HIGH=0`. RESET polarity
is `PITC_S88_RESET_ACTIVE_HIGH` (default 1).

## Also not yet wired up

- **Module/bit count**: defaults to 5 modules x 16 bits = 80 contacts
  (`PITC_S88_MODULE_COUNT` / `PITC_S88_BITS_PER_MODULE`). A single 5217
  is 1 module, so set `PITC_S88_MODULE_COUNT=1`.
- **CAN device UID / hash**: S88 change events are published onto `can0`
  as proper Marklin CAN "S88 Event" frames (command `0x11`), but the
  `device_uid` is a static placeholder and the CAN-ID `hash` field is
  *not* the real Marklin hash-collision-avoidance algorithm — just the
  device UID reused as a stand-in. Fine for bench testing against a
  single fixed listener (Rocrail, `candump`); not spec-correct for
  sharing a live bus with other real CS2/CS3 devices.
